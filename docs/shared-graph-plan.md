# 공유 관계도 개발 계획

링크 하나로 친구 단톡방이 함께 채우는 실시간 관계도를 만든다. 한 번에 다 만들지 않고, 하나씩 확인할 수 있는 작은 단계로 나눠서 진행한다.

## 목표 요약

- **만들 것**: 새 관계도 만들기 → 공유 링크 → 링크로 들어온 사람이 멤버 추가 → 열려 있는 모든 화면에 실시간 반영
- **대상**: 친구 단톡방. 띠·오행 정도는 알지만 사주 용어는 낯선 사람들
- **기대 반응**: 서로의 관계를 보며 단톡방에서 수다를 떠는 것
- **권한**: 추가는 링크를 가진 누구나(대신 추가 포함), 수정·삭제는 추가한 사람과 방장만
- **저장**: Firebase(Firestore + 익명 로그인). 원본 생년월일을 저장하되 화면에는 표시하지 않는다
- **디자인**: 지금의 별자리 디자인 유지. 카톡 미리보기는 고정 이미지 + 제목
- **하지 말 것**: 회원가입·로그인 강요, 남의 생년월일 화면 노출, 부정적인 궁합 문구

## 진행 원칙

- `main`은 푸시하면 바로 실제 사이트에 배포되므로, 작업은 `feat/shared-graph` 브랜치에서 한다.
- 단계마다 "만들기 → 확인 → GitHub에 커밋"을 한 바퀴로 돈다.
- 진행 순서는 **GitHub 기록 → Firebase 연결 → Vercel 배포**.
- Firebase 설정값은 저장소에 올리지 않는다(`.env.local`, Vercel 환경 변수).
- 6단계(보안 규칙)를 마치기 전에는 실제 사이트에 배포하지 않는다.

- **순서 이유**: 단계마다 되돌아갈 지점이 생기고, 지금 돌아가는 사이트를 건드리지 않는다.
- **완료 확인**
  - [x] GitHub에 `feat/shared-graph` 브랜치가 보인다
  - [x] `main`과 실제 사이트는 그대로다

### 1단계. 공유 화면으로 가는 길 (서버 없이)

- **만들 것**: `/g/<공유코드>` 주소로 들어오면 공유 관계도 화면이 뜬다. 데이터는 아직 예시 멤버. `/`는 지금처럼 혼자 쓰는 화면.
- **순서 이유**: 화면 길을 먼저 내 두면, 나중에 문제가 생겼을 때 화면 문제인지 서버 문제인지 가르기 쉽다.
- **완료 확인**
  - [x] `/g/test123`을 열면 공유 화면이 뜬다
  - [x] `/`를 열면 기존 화면이 그대로다
  - [x] 없는 주소를 열면 안내 화면이 뜬다

## B. Firebase 연결

### 2단계. Firebase 연결과 익명 로그인

- **방장이 할 일**: Firebase 프로젝트 만들기, 익명 로그인 켜기, Firestore 만들기(지역은 서울 `asia-northeast3` 추천, 나중에 못 바꿈), 웹 앱 설정값 전달.
- **만들 것**: 앱을 열면 조용히 익명 로그인. 회원가입 없이 브라우저마다 보이지 않는 번호표를 받는다.
- **순서 이유**: "추가한 사람과 방장만 수정" 규칙이 전부 이 번호표에 기댄다.
- **완료 확인**
  - [x] Firebase 콘솔 Authentication에 익명 사용자가 생긴다
  - [x] 시크릿 창으로 열면 사용자가 하나 더 생긴다
  - [x] 설정값 파일이 `git status`에 나오지 않는다

### 3단계. 공유 관계도 만들기와 링크

- **만들 것**: "공유 관계도 만들기" 버튼 → 랜덤 공유 코드로 관계도 생성(만든 사람 = 방장) → `/g/<코드>`로 이동, "링크 복사" 버튼. 없는 코드로 들어오면 안내.
- **순서 이유**: 멤버가 들어갈 "방"이 먼저 있어야 한다.
- **완료 확인**
  - [x] 콘솔에 관계도가 생기고 방장이 내 번호표로 기록된다
  - [x] 복사한 링크를 시크릿 창에 붙이면 같은 관계도가 열린다
  - [x] 없는 코드로 들어오면 "없는 관계도" 안내가 뜬다

### 4단계. 멤버 추가와 실시간 반영 (핵심)

- **만들 것**: 공유 화면에서 멤버 추가 → 서버 저장(추가한 사람 기록) → 열려 있는 모든 화면에 바로 반영. 최대 10명. 입력 화면은 지금 것을 재활용.
- **순서 이유**: 이번 업그레이드의 핵심. 권한보다 "들어오고, 넣고, 보이는 것"을 먼저 확실히 한다.
- **완료 확인**
  - [x] 일반 창과 시크릿 창을 나란히 띄우고 한쪽에서 추가하면, 다른 쪽에 새로고침 없이 별이 생긴다
  - [x] 화면 어디에도 남의 생년월일 숫자가 보이지 않는다

### 5단계. 수정·삭제 버튼 (화면)

- **만들 것**: 내가 추가한 멤버에만 수정·삭제 버튼. 방장은 모든 멤버 삭제 가능. 다른 사람에겐 버튼이 보이지 않는다.
- **순서 이유**: 화면에서 버튼을 숨기는 것과 서버가 막는 것은 다르다. 화면 동작부터 맞추고 잠금은 다음 단계에서.
- **완료 확인**
  - [x] 시크릿 창에서는 내가 넣은 멤버에 버튼이 없다
  - [x] 방장 창에서는 모든 멤버에 삭제 버튼이 있다

### 6단계. 서버 보안 규칙 잠그기

- **만들 것**: Firestore 규칙. 관계도 목록 통째 조회 금지, 코드를 아는 관계도만 읽기, 추가는 누구나, 수정·삭제는 본인과 방장만, 입력값 검사. 처음의 "테스트 모드"는 여기서 닫는다.
- **순서 이유**: 접속 키는 공개되는 구조라 진짜 방어는 이 규칙이다. 기능을 다 만든 뒤에 잠가야 "규칙 탓인지 버그인지" 헷갈리지 않는다.
- **완료 확인**
  - [x] 시크릿 창에서 남의 멤버를 억지로 지우려 하면 거부된다
  - [x] 방장 창에서는 지울 수 있다
  - [x] 관계도 목록 조회가 거부된다
  - [x] 실제 요청으로 허용·거부를 한 번 더 확인한다 (시뮬레이터 대신, 아래 표)

**6단계 규칙 확인 결과**

| 시도 | 결과 |
| --- | --- |
| 공유 코드로 관계도·멤버 읽기 | 허용 |
| 관계도 목록 통째 조회 / 모든 관계도 멤버 가로질러 조회 | 거부 |
| 방장 아닌 사람이 남의 멤버 삭제·수정 | 거부 |
| 방장이 남의 멤버 삭제 | 허용 |
| 방장이 남의 멤버 수정 | 거부 |
| '추가한 사람'을 남으로 적어 멤버 추가 / 내 멤버의 '추가한 사람' 바꾸기 | 거부 |
| 날짜 형식이 틀린 멤버 추가 / 없는 관계도에 멤버 추가 | 거부 |
| 남을 방장으로 적어 관계도 만들기 / 관계도 이름 바꾸기 | 거부 |
| 관계도 만들기, 내 멤버 추가·수정·삭제 | 허용 |

### 7단계. 단톡방용 마무리

- **만들 것**: 카톡 미리보기 카드(고정 이미지 + 제목), 참여 화면 문구를 쉬운 말로, 빈 화면·에러 안내 문구. 혼자 쓰기 모드는 유지.
- **순서 이유**: 기능이 다 돌아간 뒤에 겉모습을 다듬어야 두 번 일하지 않는다.
- **완료 확인**
  - [x] 처음 보는 사람이 설명 없이 30초 안에 자기를 추가할 수 있다
  - [ ] 카톡 미리보기는 8단계에서 확인

## 일정이 빠듯할 때

- 7단계의 문구 다듬기는 일부 미룰 수 있다.
- 6단계(보안 규칙)는 건너뛰지 않는다. 이 단계 없이는 실제 배포를 하지 않는다.

## 알고 감수하는 한계

- 카톡 링크는 카톡 안 브라우저로 열린다. 나중에 다른 브라우저나 다른 폰으로 열면 다른 사람으로 인식되어 내 정보를 직접 고칠 수 없다. 이때는 방장이 정리한다.
- 관계도 하나에 최대 10명은 화면에서만 막는다. 보안 규칙에서 인원수를 세려면 비용이 커서 넣지 않았다.
- 생년월일은 화면에 표시하지 않지만, 링크를 가진 사람이 기술적으로 데이터에 접근하는 것까지 막지는 않는다.
